# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal Arch Linux dotfiles for a totally custom Hyprland desktop (not built on Omarchy, though some ideas/scripts are borrowed from it — a few scripts reference `$OMARCHY_PATH/install/packages.pinned` and `packages.ignored`, which are optional/external and not required for this setup to work). A future migration to Omarchy is being considered but hasn't happened. Theming is Tokyo Night throughout (waybar, walker, alacritty, ghostty, lazygit, sddm, wallpapers).

There is no build/lint/test tooling — this is a config/scripts repo deployed onto a live system.

## Deployment model

Files are organized as **GNU Stow packages**, one per top-level directory, each mirroring the path it should occupy relative to a target root:

- `applications/` → `.local/share/applications/*.desktop` + icons (stow target: `$HOME`)
- `bin/` → shell scripts meant to end up on `$PATH` (stow target: `/usr/local/bin`, run as `sudo stow -t /usr/local/bin bin` — root-owned target, so this needs sudo unlike the other packages)
- `config/` → `.config/<app>/...` for every app (stow target: `$HOME`)
- `sddm/` → SDDM theme (`kr_minimal/`), `sddm.conf`, and `sudoers.d/` (these are system paths like `/usr/share/sddm/themes/`, `/etc/sddm.conf.d/`, and `/etc/sudoers.d/`, not `$HOME`-relative — not stowable as-is, always a manual copy/install)

`README.md` documents the pattern with one example: `stow -t "$HOME" hypr` (stow each package directory into `$HOME`; treat this as the template for `applications` and `config`). `sddm` needs to land elsewhere on the filesystem (system paths like `/usr/share/sddm/themes/`), so don't assume plain `stow -t "$HOME"` handles it.

When editing, always edit the file under its package directory (e.g. `config/.config/hypr/keybindings.conf`), never a deployed copy under `$HOME` — the repo is the source of truth and gets symlinked out.

## Architecture

**Hyprland (`config/.config/hypr/`)** is the core, and as of Hyprland 0.55 uses the new **Lua config format** (`hyprlang`/`.conf` is deprecated and was fully migrated away from here). `hyprland.lua` is the entrypoint and `require()`s the rest, mirroring the old `hyprland.conf` source order: `defaults.lua` (program vars, e.g. `terminal`/`menu`, returned as a table other modules `require`), `monitors.lua` (rules keyed by `desc:` — physical monitor make/model/serial from `hyprctl monitors all` — rather than port name like `DP-5`, so work/home monitor sets can coexist there with nothing to toggle when switching locations; a rule for a monitor that isn't connected is just ignored), `autostart.lua`, `env.lua`, `permissions.lua`, `lookAndFeel.lua`, `input.lua`, `keybindings.lua`, `workspaces.lua` (window rules only, despite the name — inherited from the old filename), `plugins.lua`, `startupApps.lua` (launches specific apps at login and pins each to a vdesk/monitor/special-workspace via the `window.open` event — see the caveats documented at the top of that file, it's the least battle-tested piece of the Lua config). The old `.conf` files for these are still present but inert (Hyprland only checks for `hyprland.lua` at startup and prefers it when found) — kept as a fallback; delete/rename `hyprland.lua` to revert to them. `hypridle.conf`, `hyprlock.conf`, `hyprpaper.conf` are **not** part of this — they configure separate hyprwm tools with their own hyprlang parsers and were intentionally left as `.conf`. Keybindings use the `description` bind flag throughout (equivalent to the old `bindd`), so `hyprctl binds -j` stays self-documenting for the keybindings menu. `autostart.lua` launches waybar, hyprpaper, hypridle, mako (notifications), and the `walker`/`elephant` user services via `hl.on("hyprland.start", ...)`, plus enables the `hyprland-virtual-desktops` plugin via `hyprpm`; virtual-desktop dispatchers (`vdesk`, `movetodesk`, `stickyrule`, etc.) are called through that plugin's Lua wrapper, `hl.plugin.virtual_desktops.*`, guarded with a nil-check since the plugin may not be loaded yet when the file is parsed.

**App launcher stack**: `walker` (the launcher UI, `config/.config/walker/`) is driven by menu/provider definitions in `config/.config/elephant/menus/` (TOML for static menus, Lua for dynamic ones like `hypr-keybindings.lua` and the `nvim-shortcuts-*.lua` files that introspect Neovim bindings). `hypr-keybindings.lua` builds its menu from `hyprctl binds -j` at runtime, not by parsing the Hyprland config source, so it works unchanged regardless of `.lua` vs `.conf`. Most `$mainMod + F1..F5`/other keybindings in `keybindings.lua` just invoke `walker -m menus:<name>` against one of these menu definitions — when changing what a menu shows, edit the corresponding file in `elephant/menus/`, not the keybinding itself. The `$mainMod F2` "Open Config Menu" entries are a static list in `config/.config/walker/json/config_files.json` (one entry per config file, hardcoded to open it in `nvim`) — a renamed/added hypr config file needs a matching update there. Walker's own visual theme lives in `config/.config/walker/themes/tokyo-night/`.

**Waybar (`config/.config/waybar/`)**: `config.jsonc` defines modules, most of which are backed by small polling scripts in `bin/waybar-*` (cpu, memory, mic, bluetooth, vpn, teams unread count, etc.) rather than waybar's built-in modules — when a waybar module misbehaves, the actual logic is almost always in the matching `bin/waybar-<module>` script, not in `config.jsonc`. Custom icon font (`kr-icons`) is generated/exported into `resources/fonts/`, with `bkp/` holding a previous export.

**`bin/`** is a flat collection of standalone utility scripts (no subdirectories), covering: pacman/AUR package management via fzf (`pkg-install`, `pkg-remove`, `pkg-aur-install`, plus non-interactive `pkg-add`/`pkg-drop`/`pkg-present`/`pkg-missing` used by other tooling/scripts), Magento Docker workflows (`launch-mage-docker`, `start-/stop-/run-magento-docker`, `cleanup-magento-docker`), Microsoft Teams unread-count polling (`teams-notifications-listener`, `teams-reset-count-on-focus`, `teams-open`, wired up as the systemd user services in `config/.config/systemd/user/`), waybar module backends (`waybar-*`), and misc desktop glue (`wallpaper-toggle`, `hyprpaper-restart`, `webapp-install`/`webapp-launcher`, `scratch-create`, `show-done`, `startup-apps` — manual trigger for `startupApps.lua`'s placement logic, see above). Scripts call each other by bare name (e.g. `pkg-install` calls `show-done`), which only works once `bin/` is on `$PATH`. `wallpaper-toggle` also calls `sudo sddm-sync-wallpaper` to copy the newly-selected wallpaper into the deployed SDDM theme (`/usr/share/sddm/themes/kr_minimal/bg.jpg`, root-owned, outside `$HOME`) — passwordless via the NOPASSWD rule in `sddm/sudoers.d/` (not stowable, installed manually like the rest of `sddm/`), scoped to that one script with no arguments since it runs unattended from a keybind with no terminal for a password prompt.

**Theming**: `config/.config/themes/tokyo-night/` holds the wallpaper set (zipped) that `wallpaper-toggle`/`hyprpaper` cycle through. Per-app Tokyo Night styling is duplicated across `alacritty`, `ghostty`, `waybar/style.css`, `walker/themes/tokyo-night/`, `lazygit`, `Kvantum/Kvantum-Tokyo-Night`, and `sddm/kr_minimal` — there's no shared token/palette file, so a color change generally needs to be repeated per app.
